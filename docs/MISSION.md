# Mission

## What Tricky World is

Tricky World is Patrick's personal corner of the internet and his engineering laboratory.

> Tricky World is my personal engineering playground — a place to turn ideas into working software, experiment with technologies, and develop the ability to build things independently.
>
> The goal isn't to accumulate frameworks or build the most complicated architecture. It's to understand how software works, make thoughtful technical decisions, and progressively become capable of taking an idea from concept to production.
>
> **Start simple. Build something useful. Understand it. Improve it. Repeat.**

The website is both a **product** (something Patrick enjoys building and using) and a **learning environment**.

## Why

Patrick is an experienced data engineer (Python, SQL, Snowflake, AWS, event-driven architectures, data pipelines, Terraform, data modelling) moving towards engineering management. The long-term goal is to become a well-rounded software engineer who can independently **design, build, deploy, operate and evolve** real applications, by building real things rather than doing disconnected tutorials.

Areas he wants to get much stronger in:

- Frontend engineering, React, TypeScript
- Full-stack and web application architecture
- APIs and backend services
- Operational databases
- Authentication and security
- Testing and CI/CD
- Containerisation and cloud application deployment
- AI application development
- Production observability
- System design

The aim is to be comfortable across the whole software lifecycle:

```
Idea → Product design → Architecture → Implementation → Testing → Deployment → Monitoring → Iteration
```

## Guiding principles

- **Start simple.** Use the simplest technology that meets current requirements.
- **Learn progressively.** Introduce a technology when a feature gives a reason for it.
- **Prefer modularity.** Don't couple unrelated applications. A gym tracker can be its own deployed app.
- **Build real products.** Working software over theoretical exercises.
- **Understand the fundamentals.** Know what the framework is doing for you.
- **Document decisions.** Record why, not just what ([DECISIONS.md](DECISIONS.md)).
- **Automate repetitive work.** Testing, linting and CI/CD where they add value.
- **Security by design.** Never commit secrets.
- **Keep costs low.** Free tiers first; explain costs before adding paid services.
- **Maintain ownership.** Patrick should understand how everything works, not just accept generated code.

## What success looks like

Not the number of frameworks used. Success is being able to take a new idea, choose a sensible architecture, build it, ship it, run it, and explain the trade-offs, without needing a tutorial.
